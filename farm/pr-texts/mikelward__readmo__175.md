# Fix stuck loading states: bound the NetworkOnly item_state read so a stalled backend can't hang every feed read

## Symptom

- Home feed stuck on **"Checking for new items…"** at the bottom of the list.
- Every grouped feed section's **"More"** stuck on **"Loading…"**.
- (Article page also fails to load under the same stalled-backend condition — see below.)

## Root cause

This branch's `item_state` re-pull commit (`a887c9c`) moved `item_state` reads from the **NetworkFirst** REST Workbox route — which had `networkTimeoutSeconds: 10`, so the read always settled (network → cache fallback) — to a dedicated **NetworkOnly** route with **no network timeout and no cache fallback**.

`feedView` and `getItemsByIds` `await this.ensureHydrated()` *before* returning rows. So when the backend stalls (a connection that's established but never answers), the item_state read hangs forever, and with it the entire feed read:

- The home feed query's `isFetching` never goes false → the background-refresh strip sticks on "Checking for new items…".
- Each grouped section's "More" is gated on that same `isFetching` → sticks on "Loading…".

The code and `SPEC.md` already *claimed* this read was "live or it fails" — but with no timeout it was actually "live or it **hangs**". (A clean failure was always fine: it rejects, `ensureHydrated` clears its memo, and the read proceeds on the last-good store. Only an open-but-silent stall hangs.) All 1063 existing tests passed because mocked fetches resolve instantly.

The article page (`getItem`, which doesn't await hydration) isn't hung by *this* path; it goes through the NetworkFirst `items` route and fails the same way any read does when the backend is fully unreachable — but the home-feed hang is the new, reproducible regression this branch introduced.

## Fix

Give the item_state read a client-side **abort timeout** (`ITEM_STATE_READ_TIMEOUT_MS = 10s` — the same bound the removed NetworkFirst route applied), implemented with `AbortController` + `setTimeout` (so fake timers can drive it in tests, mirroring `confirmBackendReachable`). On a stall the read now aborts and fails within the budget; `ensureHydrated` clears its memo and the awaiting feed/library read falls through to its RPC on the last-good localStorage store — exactly what the offline path already does. A merely-slow (not hung) read under 10s is unaffected.

## Tests

- New regression test: a `getHomeItems()` whose item_state read never returns now **resolves** (serving the feed via server-side RPC filtering) instead of hanging. Verified it fails (5s test timeout) without the fix and passes with it.
- Fake client gains `abortSignal()` + a `hangSelectOn()` control to simulate the stall.
- Full suite (1064), lint, typecheck all green.

# Fall back to DuckDuckGo's lite endpoint when web_search hits a bot challenge

# Description

The `web_search` builtin scrapes `html.duckduckgo.com`, which aggressively challenges datacenter IPs — deployed agents (which always run in cloud sandboxes) routinely got `{"error":"Search provider returned a bot-detection challenge — try again later"}` instead of results (seen live searching for the Watchfire wildfire API).

This PR makes the tool resilient instead of giving up on the first challenge:

- **Lite-endpoint fallback**: on a bot challenge, HTTP error, or thrown fetch from the primary endpoint, the search retries once against `lite.duckduckgo.com/lite/`, which serves a plainer page under a separate rate-limit bucket (with its own parser for its `result-link`/`result-snippet` table markup). Only when both fail does the tool return an error — the primary's.
- **Broader challenge detection**: DDG's modern anomaly interstitial ("Unfortunately, bots use DuckDuckGo too", `anomaly-modal`) now counts as a challenge, not just classic CAPTCHA markers.
- **Browser-like headers**: requests now send `Accept`/`Accept-Language` alongside the UA — a bare UA with no Accept headers is an easy bot signature.
- The DuckDuckGo scraping moved from `builtin-tools.ts` to its own `host/web-search.ts` (the former was approaching the 500-line file cap).

## Why

Keyless web search is what every agent and the studio's coding agent rely on; a single challenged endpoint made it fail routinely from cloud IPs with nothing to do but "try again later".

# fix(retention): purge mid-call transcript turns that never got a recording (#1202)

Fixes #1202.

## The defect
`persistTurn` in `voice-session-store.ts` writes every mid-call utterance to `call_transcript_turns` with `voice_recording_id` NULL. Only the recording webhook's `attachRecording` links those rows to a recording later. The retention sweep (`recording-retention-worker.ts`) deleted turns in one place only: `purgeDerived`, with `WHERE tenant_id = $1 AND voice_recording_id = $2`, for recordings past retention. So a call that never got a recording kept its caller and agent transcript forever, whatever the tenant's `recording_retention_days`. That covers Media Streams calls (no `<Record>`), Gather calls with storage or Twilio credentials unset, and failed uploads.

## The fix (one file: `packages/api/src/workers/recording-retention-worker.ts`)
The sweep gets a second phase. It runs after the recording drain, and also runs when `findDue` fails.

- **Selection (cross-tenant):** `findTenantsWithDueUnattachedTurns` runs under `withCrossTenantSweep`, like `findDue`. It starts from `tenant_settings` and uses a `LATERAL` probe to find tenants that have `voice_recording_id IS NULL` turns with `created_at < now - make_interval(days => recording_retention_days)`. Oldest backlog comes first, with at most 100 tenants per sweep. `EXPLAIN` shows `Index Scan Backward using idx_call_transcript_turns_tenant` for each tenant, so no hourly full scan of the turns table and **no migration**.
- **Deletion (tenant-scoped, bounded):** `purgeUnattachedTurns` runs under `withTenantTransaction` and deletes at most 1000 rows per tenant per sweep, oldest first. It reads the horizon again from `tenant_settings` inside the DELETE. The outer `AND t.voice_recording_id IS NULL` is re-checked on the row version the DELETE locks, so a concurrent `attachRecording` wins and the row is left for the recording path.
- **Legal hold on the call's recording (review round 1):** `voice_recording_id IS NULL` does not mean the call has no recording. The voicemail leg (`voicemail-status-route.ts` → `recordInboundCall`) never attaches turns, and `recording-transcript-hook.ts` swallows a failed `attachRecording` that no Twilio retry repeats. Both the tenant selection and the DELETE now require `NOT EXISTS (SELECT 1 FROM voice_recordings vr WHERE vr.tenant_id = ctt.tenant_id AND vr.call_sid = ctt.call_sid AND vr.legal_hold)`. In the DELETE it is applied twice: inside the LIMITed batch, so held rows never use up the batch and stall the drain, and again as a re-check on the deleted row. The in-memory repo does the same.
- **Failure isolation:** if one tenant's purge throws, the sweep logs `warn('recording-retention sweep: unattached-turn purge failed for tenant', {tenantId, error})`, counts it, and moves on to the remaining tenants. That tenant's transaction rolls back and its rows are retried on the next sweep.
- **Counts:** the sweep result, and the `recording-retention sweep completed` log line that already reports `due/purged/failed`, now also report `unattachedTurnsPurged` and `unattachedTurnTenantsFailed`.
- **Audit:** the event is built the same way as `voice_recording.purged`: `createAuditEvent`, actor `recording-retention-worker`/`system`, best-effort, and per-class counts under `metadata.derivedPurged`. There is one event per purged call: `eventType: 'voice_session.transcript_purged'`, `entityType: 'voice_session'`, `entityId: <CallSid>`. That entity is the one the codebase already uses for CallSid-keyed audit events (`voice-gate.ts`, `mediastream-adapter.ts`). Metadata: `{ callSid, reason: 'no_recording_past_retention', oldestTurnAt, derivedPurged: { transcriptTurns } }`. In the rare case of a row with no call_sid, the entity falls back to `tenant`/tenantId. If the audit write fails after the rows are committed, the sweep now logs `warn('recording-retention sweep: unattached-turn audit write failed', {tenantId, callSid, transcriptTurns, error})` instead of swallowing it (review round 1).
- `InMemoryRecordingRetentionRepository` implements both new

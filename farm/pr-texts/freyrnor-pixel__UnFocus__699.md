# Retire the blur's ghost: stale glass docs, and a hint that promises a blur we deleted

## Summary

Started as "make the glass look more like iOS glass" (an external suggestion to build a `<GlassCard>` around `expo-blur`). That turned out to be a no-op request — `GlassCard` already exists as an alias at `components/Surface.tsx`, and the blur it proposed is the thing we deleted on 2026-09-07 for the lag. **Nothing visual changed here.** What the investigation did surface is that `expo-blur` left the app but six comments still describe it as live, one of them user-facing.

- **Shipping bug:** `reduceEffectsHint` in EN/NO/IS told users the toggle "Turns off the blur, card shadows and background glow". There is no blur. Now names what the flag actually takes — the two-pass `boxShadow`, the pane's translucency, the backdrop orb field.
- **A pointer to a guard that does not exist:** `Surface.tsx` cited `lib/__tests__/glassPredicate.test.ts` as the protection against the constant-false `glassOn` — the defect that cost a day on 2026-09-06 and that three source-text assertions passed straight over. That file isn't in the repo; the truth-table test is in `__tests__/glassMaterial.test.ts`. A session that looks for the named guard, doesn't find it, and concludes it was never written is one step from repeating the bug the comment warns about.
- **Four more stale claims + dead code:** `colors.ts` called overlay/nav "the only places that mount a real `BlurView`" (none do); `useSettingsStore.ts` described the per-frame stack as a `BlurView` per card and a THREE-pass shadow (neither true since 09-07 / 09-09); `theme.ts` had `getGlassEdge` feeding a `LinearGradient` padding-ring deleted on 2026-08-27; `SurfaceContext`'s doc still said all three contexts "render identically", false since 2026-08-18 and it's the type that decides whether a pane is glass at all. `styles.ring` deleted — zero references.

`glassOn`, the edge ramp, the shadow passes and `glassBudget` are untouched.

## Notes

No new i18n keys — three existing values rewritten (`reduceEffectsHint`, EN/NO/IS). No migrations, no native-surface changes. Ships over OTA.

**Two things deliberately left out, for your call:**

1. **Brightening the card's lit rim** was the only glass parameter with no contrast constraint binding it (`glassBudget`'s `border ≥ 3:1` measures the *shade* stop). But `glassMaterial.test.ts` pins `litDark` to the `0.1x` range, so the available move is `0.16 → 0.19` — which computes to a **7/255** change on a 1.5px stroke. For reference, the visual gate once reported a 46,329-pixel 1-level change as `unchanged`. A visible rim needs ~0.30 (31/255) and a regex edit, which `DESIGN_COMPARISON/16` §2 says is a maintainer conversation, not a quiet test edit.
2. **`expo-blur` is still in `package.json` with zero imports**, so it autolinks a native module into the Android build for nothing. Small real win for the lag, but it's a native change needing a `runtimeVersion` bump per `OTA_BUILD_WORKFLOW.md` — it belongs in its own PR, not this one.

Worth knowing for the original question: the pane transmits 86%, but the washes behind it were halved to keep text legible, and `glassBudget.test.ts` records that the binding constraint clears by only ~5%. There is no large free win left in this material on Android — `borderCurve: 'continuous'` (Apple's squircle corners, zero per-frame cost) is a silent no-op there.

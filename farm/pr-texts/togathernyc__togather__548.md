# fix(datepicker): use MUI Desktop Date Picker on web

## Problem

On the desktop (web) build, the shared `DatePicker` rendered a native HTML `<input type="datetime-local">`. It bound a **UTC** ISO string (`value.toISOString()`) into a control that reads and writes **local** time, so the displayed value and the parsed value used different timezones. Typing or picking a value jumped to a seemingly random date.

Repro (from the report): Create Event → Date & Time → type/select a date → picker snaps to a random date.

## Fix

Replace the web branch with the **MUI Desktop Date Picker** (`@mui/x-date-pickers`), which parses and formats consistently in local time.

- New `apps/mobile/components/ui/DatePicker.web.tsx` — Metro resolves `.web.tsx` for the web bundle, so MUI/emotion **never reach the native iOS/Android bundles** (native fingerprint unchanged, verified).
  - Uses `DesktopDatePicker` / `DesktopTimePicker` / `DesktopDateTimePicker` based on `mode`.
  - Only propagates a cleared value (`null`) or a fully valid `Date`, ignoring the `Invalid Date` MUI emits mid-typing — this is what kills the "random date" jump.
  - Themed to the community `primaryColor` and light/dark palette so it matches the app's design.
- `apps/mobile/components/ui/DatePicker.tsx` — removed the broken web branch (now lives in `.web.tsx`) and the unused `handleDateSelect`. Native iOS/Android behavior is unchanged.
- Added `@mui/material`, `@mui/x-date-pickers`, `@emotion/react`, `@emotion/styled` to the mobile package.

The two other files that import `@react-native-community/datetimepicker` directly (`FollowupDetailScreen`, `CommunicationBotConfigModal`) gate rendering behind `Platform.OS === "ios"/"android"`, so they never render on web — the shared `DatePicker` is the only web-facing picker.

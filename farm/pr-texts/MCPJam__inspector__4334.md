# Evals v2 — G4b: the inspector half of pre-run disclosure

## Summary

This is the **inspector half of Evals v2 Lane G, step G4** (task ID `g4b`). The backend half — [`g4a`, mcpjam-backend#1119](https://github.com/mcpjam/mcpjam-backend/pull/1119) — is merged and **deployed to staging**, computing the whole pre-run disclosure contract (`testSuites:getRunDisclosure`). **The production promote is still owed**, so this entire surface is inert on prod until that fires: the new route will answer `contract_unavailable` there until the backend query is live in production.

What "pre-run disclosure" means: what happens to a run's content *before* you launch it — which models it calls and where they route, whether LLM analyzers/judges fire and where their evidence goes, capture/retention/region facts, and the subprocessors engaged. This PR projects that backend contract, never recomputes it.

- **Route** — `GET /v1/projects/:projectId/eval-suites/:suiteId/run-disclosure` (`server/routes/v1/eval-disclosure.ts`), mirroring `capabilities.ts`'s idioms. It composes `execution.locus` from `HOSTED_MODE` (the backend reserves this field — only the inspector process knows whether it's MCPJam-hosted or the caller's own machine) and answers an explicit `422 FEATURE_NOT_SUPPORTED` / `details.reason: "contract_unavailable"` on a backend too old to have the query, rather than a partial or reassuring payload. Unknown top-level sections a newer backend adds pass through structurally (shallow spread), not dropped by a hand-typed projection.
- **SDK** (`@mcpjam/sdk/platform`) — `PlatformEvalRunDisclosure` + sub-types (hand-mirrored from `convex/lib/evalDisclosure.ts`, field names identical), `PlatformApiClient.getEvalRunDisclosure`, and a read-only `get_eval_run_disclosure` operation. `PlatformOperationContext` gains `onDisclosure`; `runEvalSuiteOperation` fetches the disclosure once against the **frozen launch plan**, fires `onDisclosure`, and returns it on the receipt's `disclosure` field — all before `createEvalRun`/`createEvalRunGroup`. One resolution, so "what was disclosed" is literally "what will run" — no second target resolution that could drift. Best-effort: a disclosure fetch failure never blocks or fails the launch. Registered in `agent-op-registry.ts`, so it flows into the MCP tool catalog.
- **CLI** — `writeRunDisclosure` (twin of `writeRunGroupSummary`) prints the block in human mode, strictly before the run link; `--format json` carries `disclosure` inside the single receipt document, unchanged byte shape otherwise.
- **UI** — `use-run-disclosure.ts` (same fetch-on-open/request-id-ordering shape as `use-run-cost-estimate.ts`, but over `authFetch` via a wrapped `PlatformApiClient` rather than `useConvex()`) and `RunDisclosureHint`/`SuiteRunDisclosureHint` (sibling of the cost-estimate hint), wired beside `SuiteRunCostEstimateHint` in `suite-header.tsx`. `ReviewStep.tsx` gets an optional, props-only `runDisclosureState` slot (the component never fetches its own data) — this wizard has no suite id until the final confirm, so no caller threads a live hook state into it yet, but the contract is in place for when one does. **Read-only, never gates, disables, or delays a run.**
- **`execution` vs `executionAbsence`** render *different* copy everywhere (CLI + UI), and the two `executionAbsence` kinds (`ingested-run` vs `plan-unresolved`) render *different* copy from each other — rendering the ingest wording for an about-to-launch plan would tell a user nothing leaves when it's about to call models. That bug was fixed once on the backend in g4a; this PR is careful not to reintroduce it at the presentation layer.

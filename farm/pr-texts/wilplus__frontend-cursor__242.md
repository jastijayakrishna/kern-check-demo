# Split style-src so injected &lt;style&gt; blocks are blocked

`FILTER: ADVANCE-F1-SURFACE — cat {F1-SURFACE} — fences {clear} — locks {clear} — redirect: n/a`

Follow-up to the nonce CSP (#228): `style-src` still carried `'unsafe-inline'` — the last escape hatch left in the policy.

## Why it can't just be removed

A nonce never applies to a style **attribute**, only to `<style>` **elements**. And hashing is out, because every inline style in this app carries a runtime-computed value:

| Component | Style |
| :--- | :--- |
| `MediaPlayer` | `width: fillPct` (playback progress) |
| `SnippetReadoutBlock` | `left: ${pos}%` |
| `coach/audit` | `width: ${pct}%` |
| `LoadingState` / `ErrorState` | `height/width: size`, computed `inset` |
| `LibraryOverlay` | `height`, `width: thumbW` |
| `JournalCard`, `game` | `height: ${h}%` / `${h}px` |

Dropping `'unsafe-inline'` outright would blank every dynamically-sized element in the app. CSS custom properties don't rescue it either — setting one is itself a style attribute.

## What this does instead

The CSP Level 3 split takes the half that *is* achievable:

```
style-src      'self' 'unsafe-inline'   # Level 2 fallback, unchanged
style-src-elem 'self'                   # no inline <style>, no third-party sheets
style-src-attr 'unsafe-inline'          # React's computed style= attributes
```

That closes the vector an injection would actually exploit at scale: a single `<style>` block can carry selectors that exfiltrate attribute values a character at a time, whereas a style attribute only restyles the one element it sits on. `style-src` stays beneath them as the fallback for browsers that don't implement the split, so nothing regresses on older engines.

## Verification

- **all CSS is same-origin** (`/_next/static/css/…`) on every page checked, including `/dashboard`

## Note for a reviewer

`style-src-attr` / `style-src-elem` are CSP Level 3. Browsers that support them **ignore** `style-src` for those resource types; browsers that don't fall back to `style-src`, which is unchanged. Either way the policy is no looser than today.

One thing deliberately **not** included: `img-src` still allows blanket `https:`, which is the channel CSS-based exfiltration would use. Tightening it is a separate call, since blog cover images come from backend-supplied URLs and I'd want the real host list before narrowing it.

# fix(shader-dsl): guard df64_mul cross terms against distributive fast-math

## What

Threads the runtime-opaque `one` guard through `df64_mul`'s (and `df64_vN_mul`'s) **cross terms**, the last multiply path that lacked the anti-fast-math wall `df64_twoSum` / `df64_twoSqr` already carry.

## Why

On-device, the df64 probe on an iPhone (Apple GPU, both WebGL2 and WebGPU) showed the loaded-lo class fully fixed by #915/#916 — `sub`, `neg`, `abs`, `fract`, `mix`, `loran`, `vec_sub_ld`, `vec_div`, `vec_fract`, `dg_sub_*`, `dg_launder*` all **PASS**. The remaining failures were **all** the multiply family: `mul` → 0, `vec_mul` → 0, `div` → wrong (its Newton step multiplies), `dg_mul*`, and the mul-containing random-composition trees.

The tell was the **exact-zero** output. `1e8 · 5e-9 = 0.5` is an exactly-representable f32 product; a merely lossy multiply would read ~0.5, not 0.0. An exact 0 is a *deleted* term, not a mis-rounded one — i.e. the compiler factored

```
a·b_hi + a·b_lo  →  a·(b_hi + b_lo)
```

and `b_hi + b_lo` rounds back to `b_hi` in f32, deleting the cross term and collapsing the product to f32 precision. This is a **compiler reassociation** (fixable inside the shader), not the lossy-ALU class.

Two facts in the source confirm the diagnosis:
- `df64_twoSqr` (used by `sqrt`) already guards each error term with `* one` — and `sqrt` **passes** on the same device.
- `df64_twoProd` / `df64_mul`'s cross terms had **no** `one` guard — and `mul_sq` passed only because its operand's lo is 0, so the cross term never forms.

## How

```ts
// df64_mul — cross terms now threaded with `one` (distinct multiplicities,
// as df64_twoSqr's error terms are, so neither can be factored back in)
prod.y.assign(prod.y.add(p.a.x.mul(p.b.y).mul(one)))
prod.y.assign(prod.y.add(p.a.y.mul(p.b.x).mul(one).mul(one)))
```

Same change in the vec64 `df64_vN_mul`. `df64_twoProd`'s split-error path is left as-is — `mul_sq` proves it holds on-device, so it stays surgical.

## Verification

- `tsc` clean; **591/591 shader-dsl tests green**, including the oracle metamorphic gate and the fround-mirror known-answer suite — `* one` is `* 1`, so every value is unchanged and no correctly-rounded GPU regresses.
- Package build green.
- Rebakes the 20 fp64 example goldens that use a df64 multiply; the guard shows as `(a.x * b.y) * _fp64_texel` in each `df64_mul` body.
- **On-device is the final gate**: after deploy, `mul` / `vec_mul` / `div` and the Apple-only mul-family random trees should flip to PASS on the iPhone.

## Scope note

The random-composition trees that fail on **both** Apple and NVIDIA Blackwell (rand 00/04/05/06/07/09/15/18/19/20/21) are a separate, harder class — a fast-math reassociation *across* the composed expression that a per-op guard can't reach — and are **not** addressed here. Only the Apple-specific mul-family is.

# Fix scaleZ not being applied to the transform

<!-- claude-projects-attribution: {"github_login":"mattgperry"} -->
_Requested by **Matt** · [project thread](https://claude.ai/code/project/chan_01DCHat6Av93snyBPyTtQqPD?thread=cmsg_01DCHat6Av93snyBPyTtQqPDWdA9AN2Pea2xMJqLzDdjKP)_

**Before:** `scaleZ` set through `initial`/`animate`/variants or `style` never made it into the element's `transform`. `scaleX`, `scaleY`, `rotateZ` and `translateZ` all worked. For example, `animate={{ scaleZ: 2, rotateX: 45 }}` rendered `transform: rotateX(45deg)`.

**After:** `scaleZ` is a first-class transform. It's written as `scaleZ(n)` between `scaleY` and the rotations, omitted at its default of `1`, and composed through the same paths as the other transforms (`buildTransform`, the style effect, WAAPI transform groups and unit conversion).

**How:** `scaleZ` was missing from `transformPropOrder`, so `transformProps` didn't recognise it and it was treated as a plain style. The fix adds it after `scaleY`. Every consumer that enumerates transforms derives from that array, so they all pick it up. The value type and `scale*` default handling already existed. `parseValueFromTransform` also gets `scaleZ` parsers so that reading it from the DOM returns the identity `1`. Without them a read would come back `undefined` and fall back to an animatable-none of `0`. The `matrix3d` parser uses the column length (`hypot(m13, m23, m33)`) and the 2D `matrix` parser returns `1`. The 3D `scaleX`/`scaleY` parsers now use `Math.hypot` too. The maths is the same, and it keeps the style-effect bundle within budget. Projection is untouched: `scaleZ` alone doesn't distort the 2D layout box, and combined with a rotation the existing rotate reset already covers it.

Fixes #2609

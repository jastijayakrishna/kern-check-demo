# feat(core): the daemon's file work in core's home runs as core (#559, 3 of 5)

Part of [#552](https://github.com/actana/control/issues/552). Refs #559. PR 3 of 5 for #559 (PRs 1 and 2 are merged; PR 4 turns the privilege model on).

## Summary

In the container the daemon will be its own user and `core`'s home is 0750 core:core. Every short write or check the daemon made there (hook files, `~/.claude/settings.json`, skill folders, the registry blob, a cwd check, a directory listing) would fail with EACCES. They now run in a short-lived **helper**, started through `asCore`: one JSON request on stdin, one JSON answer on stdout, a new bundle entry beside the daemon's. Dormant outside container mode: the client handles the same request in process, so metal installs and the old tests are unchanged.

```
packages/core/src/
  core-home-ops.ts          the helper's half: 8 operations, request validation, path confinement (also what runs in-process on metal)
  core-home-ops-main.ts     helper program: stdin -> handler -> stdout; exit 0 result / 1 failed / 2 refused, reason on stderr
  core-home-ops-entry.ts    bundle entry -> dist/core-home-ops.cjs (packages/core/build.mjs; staged into the tarball's app/)
  core-home-ops-client.ts   daemon side: asCore(node, bundle), sync + async, kill-as-core on a hung helper, one *ViaCore per operation
daemon call sites (none imports fs or a writer any more)
  pty-manager     spawn policy's cwd check + realpath (one request per spawn), statusline tap, harness hooks (harness-hooks, -pi, -opencode), Shift+Enter flag
  core-exec       resolveCwd
  core-entry      orchestration skill install, dirList
  core-self-register   registry blob (daemon signs the bearer; the helper never sees bearerSecret)
orchestration-skill.ts  install split from its logging, so the helper can run it silently
```

The helper never runs with the daemon's env (`asCore` builds a clean one, and the helper refuses to start if any `AC_` variable, except `AC_HOOK_`, is present). Its root is its own `HOME`. A request must name one of the eight operations, with no unknown fields; every path must be under the home once normalised **and** resolve under it through `realpath` (a symlink that leaves the home, or a dangling one, is refused, not followed). That covers the files the writers derive too, not only the directory they start from: each hook file (`.claude/settings.local.json`, `.codex/hooks.json`, `.cursor/hooks.json`, the opencode plugin, Pi's extension), the tap script and its settings file, and every Harness skill folder are confined before the writer runs. Every request is async with a 15 s deadline; past it the helper is killed through `killAsCore`.

**Not in this PR, by design:** the Files API (`files-tar.ts`, `buildCoreFileRoutes`) moves with #557 (the orchestrator's recommendation on #559 D5) and is untouched. No Dockerfile, compose, entrypoint or smoke change (PR 4).

## Merge danger

- **Two-way door.** Outside container mode every request is handled in process with no confinement (`roots: null`), and the variables that switch container mode on are still not set by the image (PR 4). Reverting is a plain revert.
- **Blast radius:** every Session spawn (three helper processes per Claude Code spawn: path facts, tap, hooks; one for other harnesses), boot (skill install, Shift+Enter, registry), `core exec`, and the folder picker. Hang cost: the deadline is **per request**, and a Claude Code spawn makes three awaited requests in turn (path facts, tap, hooks). A systemic hang (a stuck mount) therefore costs a Claude Code start up to **30 s** (tap and hooks each wait 15 s, then the spawn goes ahead without hooks, `installed: false` as before); if the path-facts request hangs, the spawn **fails after 15 s** with a plain `Error` (a hang is not a policy refusal; only a refused cwd is turned into `invalid-cwd`). The event loop is never blocked while it waits, and each stuck helper is killed at its deadline. Boot (Shift+Enter, skill install, registry) waits at most 15 s per step, asynchronously; the skill watcher's re-install at runtime is fire-and-forget.
- **Behaviour that changes in container mode only:** a project root, a `core exec` cwd or a folder-picker path **outside `/home/core`** is refused, and the picker's "up" stops at the home (see low-confidence 1).
- **PR 4 prerequisites, before container mode is switched on:** (1) `createDirectory` (the picker's new-folder button, `core-entry.ts:520`) must go through the helper, or that button fails; (2) `resolveCommand` in the spawn policy (`pty-manager.ts:686`) stats `~/.local/bin` as the daemon, so an installed Harness CLI reads as missing until it does too; (3) the image ships `dist/core-home-ops.cjs` (the tarball now stages it) readable and executable by `core`, beside `core-entry.cjs`.
- **Not in this PR:** the Files API (#557), and the two PR 4 prerequisites above, which were not on the issue's list.

## Low-confidence choices

1. **Every path is confined to core's home in the container, including the read-only operations** (`dirList`, the cwd check, path facts) and `core exec --cwd`, although the issue's list says "core home or workspace" and a Session's cwd can be any project root. `core-home-ops-main.ts:81`, `core-home-ops.ts:276`. A root or exec cwd under `/tmp` or `/srv` now fails in the container. The image's only persistent place is `/home/core`, which is why I chose it.
2. The folder picker's "up" stops at the home: `parent` is `null` there (`core-home-ops.ts:423`).
3. A symlink that stays inside the home is followed; only one that leaves it (or dangles) is refused. The check-then-write is not atomic (a link swapped in between is not caught); the helper is `core`, so a Session can do the same. The derived writer files are now confined too (fix round 1).
4. (Replaced in fix round 1.) There is no sync wait; boot awaits the helper, each request has a 15 s deadline.
5. Three helper processes per Claude Code spawn instead of one request that does all three (`pty-manager.ts:676,727,742`). They are separate operations in the issue's list, and separately testable; merging them is a one-line change per call site if the ~50-100 ms each matters.
6. A project root core cannot resolve is dropped rather than falling back to its lexical path as `defaultRealpath` does (`pty-manager.ts:590`).
7. The hooks request carries only `PI_CODING_AGENT_DIR` from the spawn env, not the env (`core-home-ops-client.ts:261`). Nothing else in the hook writers reads it.
8. The self-registration credential (including the client key) goes to the helper on stdin; `bearerSecret` does not: the daemon signs (`core-self-register.ts:126`). The blob is readable by `core` on purpose anyway.
9. `CoreHomeOpsOptions.wrap` lets a caller replace `asCore` (`core-home-ops-client.ts:74`). It exists because a test cannot `setpriv`; only tests pass it, and the PR 2 guard still requires the literal `asCore(` in the file.
10. `scripts/build-core-tarball.mjs` (one staged-bundle line and its test) is outside the listed call sites, but without it the helper is not in the tarball.
11. I edited two PR 2 test files (`pty-manager-core-identity`, `core-identity-spawn-sites`): their container-mode cases for the VM shell, `core exec` and Shift+Enter used `/tmp` cwds and expected the daemon to write; they now stand the helper in.

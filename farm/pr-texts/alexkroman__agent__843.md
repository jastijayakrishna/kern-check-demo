# Show the long-living platform API URL and redirect it to the live sandbox

# Description

The API chip in the studio preview (and every default client) showed the brokered sandbox tunnel URL (`wss://ta-….modal.host/websocket`), which dies whenever the sandbox is idle-evicted or redeployed. Two changes make the displayed API the long-living one that upgrades callers to the sandbox API:

- **aai-ui**: the snapshot's `apiUrl` is pinned to the long-living platform endpoint (`wss://host/:slug/websocket`) derived at construction; it is never replaced by the per-attempt brokered sandbox session URL.
- **aai-server**: a plain WebSocket upgrade on `/:slug/websocket` now resolves the agent's live sandbox — booting it on demand, exactly like the `GET /:slug/client-config` broker — and answers `302` with a `Location` naming the sandbox's current session URL, query preserved so `?sessionId=` resumes survive the hop. Unknown slug → 404; a sandbox that failed to start → 503 (retryable), mirroring the broker. Browsers don't follow WebSocket redirects, which is fine: the browser path remains the client-config broker.

## Why

Anyone who copied the API URL from the studio held a link that rots as soon as the sandbox is replaced. The platform endpoint is stable across evictions and redeploys, and programmatic WebSocket clients that follow handshake redirects (`ws` with `followRedirects`, websocat) land on the live sandbox each time.

## How to test

- `pnpm vitest run packages/aai-server/transport-websocket.test.ts` — plain upgrades now covered for redirect, query preservation, 404, and 503.
- Connect a redirect-following WS client to `wss://<origin>/<slug>/websocket` and confirm it lands on the sandbox session.

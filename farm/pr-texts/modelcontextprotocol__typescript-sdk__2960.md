# fix(server): keep the Mcp-Param check on a tool with a number-typed header

<!-- ccr-slack-attribution -->
_Requested by **Felix Weinberger** · [Slack thread](https://ant-mcp-oss.slack.com/archives/C0BGE84P7T7/p1789215705361939?thread_ts=1789215705.361939&cid=C0BGE84P7T7)_

Follow-up to #2762.

**Before:** #2762 makes the declaration scan report a tool as invalid when it puts `x-mcp-header` on a `number`-typed parameter. `createMcpHandler` compared the `Mcp-Param-*` headers with the body only when the scan was valid, so for such a tool the whole check went away, valid string, integer and boolean parameters included: a `tools/call` whose header disagrees with the body got 200 where released 2.3.0 answers 400 with `-32020`.

**After:** The scan keeps walking after a `number` fault. When those are the tool's only faults it returns the declarations next to the reason, and the handler checks whatever declarations the scan returns. The result is still invalid, so clients still drop the tool from `tools/list` and the server still warns; `registerTool` does not throw. Between an upgraded client and an upgraded server, a call by name of such a tool is answered 400 again, as against a 2.3.0 server; with #2762 alone it was 200. A tool with another fault as well was not checked in 2.3.0 and is not checked now.

**How it was verified:** Against released 2.3.0 over 13 tool shapes and 68 request cases (status, error code, the header named in the error, whether the handler ran), `main` today differs in 20 cases and this change in 0. The new server test fails without either source change (`expected [200, …] to deeply equal [400, -32020, 'Mcp-Param-Region']`); the new client test fails as soon as `number` is permitted again. core-internal, client and server suites pass; typecheck, ESLint, Prettier, `sync-snippets --check` and `docs:check` are clean. Changeset: `@modelcontextprotocol/server` patch.

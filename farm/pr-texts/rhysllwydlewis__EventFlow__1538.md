# Reorder homepage sections for SEO/UX and fix missing alt text

## Summary

**Content order** (hero and footer untouched):

| Before | After |
|---|---|
| Featured packages | **Category browsing** |
| Spotlight packages | **City browsing** |
| Category browsing | Benefits |

Category and city browsing are the two things a visitor with real search intent ("wedding venues Cardiff") actually wants, and the two modules whose links carry real internal-link value — the city cards' live JS path already links to the indexable `/locations/:city` pages. Moving both right after the hero surfaces them immediately instead of after two live-listing carousels, and puts the highest-value internal links earliest in the DOM. Guides move up next since they're genuine indexable long-tail content, ahead of the marketplace/carousel blocks that show churning individual listings.

**Accessibility fix**: category and guide card images were rendering with `alt=""` — inconsistent with the marketplace and supplier-CTA images on the same page, which already use descriptive alt text. Both now use the category/guide title.

**Test update**: `tests/unit/location-navigation-discovery.test.js` previously asserted location discovery sits "near the bottom" of the homepage, after guides — true of the old order by design. Updated to assert the new, deliberate position: paired with category browsing near the top, ahead of guides.

## Deliberately not included in this pass

- **Changing the city cards' static-HTML fallback links** from `/suppliers?location=X` to `/locations/:city`. The live JS-rendered path already links to `/locations/:city` for cities that have actually passed the publish gate (fetched from `/api/v1/locations/featured`); the static fallback intentionally does not assume every featured city has a published guide (per PR #1534's own documented rationale — none had cleared that gate at the time). Hardcoding a direct link in the crawl-safe static fallback risks a dead link for any city that isn't actually published yet, which isn't something verifiable from this environment. Worth a follow-up once publish status for these specific cities is confirmed.
- The homepage's visual-regression pixel-diff baseline (`tests/visual/visual-regression.spec.mjs`) is already marked `screenshotApproved: false` for unrelated reasons (a prior baseline mismatch, documented inline), so it doesn't gate this change; the axe-core accessibility scan in the same spec still runs regardless of section order and is unaffected by it.
